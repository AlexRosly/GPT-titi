❓ Ответ на главный вопрос
В какой момент фронт обращается к /stream?
🔹 Правильный UX flow

Пользователь вводит сообщение

Front → /chat/preview

показать цену

проверить лимит (-200)

Пользователь нажал Send

Front → /chat/send

сервер говорит: OK, можно

Front СРАЗУ ПОСЛЕ этого:

открывает SSE / fetch stream

→ /stream

❗ /chat/send не стримит
❗ /stream не считает “можно ли”

🎯 Роль каждого роута
Роут	Ответственность
/chat/preview	оценка стоимости
/chat/send	бизнес-валидация + резерв
/stream	OpenAI + фактическое списание

🧩 ШАГ 10 — Контроллер chatSend (без дыр)
Что он делает

проверяет модель

проверяет баланс (с учётом -200)

ничего не списывает

возвращает ok

5️⃣ Архитектурно: всё теперь логично и чисто
Кто за что отвечает
Уровень	Ответственность
chatSend	можно ли начать
streamChat	OpenAI stream
chargeUserPreview	стоп по ходу
finalizeCharge	финальное списание
estimateCost	прогноз
calculateModelCost	факт

👉 Ни один слой не дублирует логику

🔐 Что мы получили
Проблема	Решение
БД дергается на каждый chunk	❌ → ✅ раз в 300 токенов
Возможен уход в минус	❌ → ✅ резерв
Двойное списание	❌ → ✅ preview ≠ finalize
Нагрузка	❌ → ✅ в разы меньше
⚠️ Важно понимать ограничения

Это решение:

✔ отлично для одного Node-инстанса

❌ НЕ для горизонтального масштабирования

👉 Для scale:

Redis

или Mongo $inc с лимитом

или distributed lock

(это будет вариант B)
