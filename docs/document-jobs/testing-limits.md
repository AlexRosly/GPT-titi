# Контрольовані ліміти для тестування документів

База патчу: main 19eae54, уже містить document-handoff-guard-v1.
Фронт оновлюється окремо: старий parser відкидає статус із runs > 5 або calls > 6.

## Що підтверджує діагностика від 13.11.2026

Запит f4aaf01a-49ff-4b3f-a24b-ba8640a379a8:
2 додаткові виклики, 3 локальні дії, 17 158 provider tokens; фонова job ще не створена.
За скріном результат partial / COMPUTE_BUDGET_LIMIT. Протокольний status=completed
означає завершення відповіді, а не успішне редагування файлу.
У ledger одне списання 9 442 TITI, один release, reservationState=settled.
reservedAppTokens=16644 у turn — збережена величина колишнього резерву, не активний hold.
Три reservation_hold — початковий резерв і його збільшення, не три списання.

Три інші запити о 11:26–11:30 за Києвом уже містять runtime нового worker,
але закрилися з активною job; queue отримала DOCUMENT_TURN_GONE на cursor=0.
failureDiagnostic.terminal відсутній. Це не дає встановити конкретного автора
запису failed і не доводить несправність збереженого Excel.
Інший/старий recovery worker — робоча гіпотеза, а не встановлений факт.

Попередній enqueue ставив leaseUntil=epoch для активної job. Старий recovery
scanner бачив її як прострочений чат. Тепер enqueue ставить job.deadline;
після публікації результату повертає epoch для штатного завершення чату.
Нові atomic guards теж залишаються. Черга продовжує перевіряти cancel,
користувача, джерело, квоту, власний lease і строк job.
Уже failed/cancelled запити й утримані за ними резерви автоматично не змінюються.

## Значення

| Обмеження | Типове значення | Рекомендовано для тестів | Межа конфігурації в коді |
| --- | ---: | ---: | ---: |
| Додатковий бюджет моделі, COMPUTE_MAX_USD | $0.20 | $1.00 | $0.001–$5 |
| Локальні дії, COMPUTE_MAX_RUNS | 5 | 12 | 1–24 |
| Додаткові виклики моделі, COMPUTE_MAX_CALLS | 6 | 16 | 1–32 |
| Сумарний час локальних дій, COMPUTE_TOTAL_MS | 180000 мс | 300000 мс | 1000–600000 мс |

Типові значення не підвищуються автоматично. Рекомендований набір є у
testing.env.example. Межі конфігурації — абсолютні обмеження допустимих
налаштувань, не значення, які треба ставити на сервері.

COMPUTE_MAX_USD — додатковий бюджет оркестрації після початкового модельного
етапу. Він НЕ є лімітом усієї вартості запиту: початковий етап оплачується
окремо, за чинними правилами V2. Фактичні тарифи беруться зі snapshot pricing
запиту. $1 не списується й не резервується наперед цілком: перед кожним викликом
перевіряються накопичені відомі витрати плюс консервативний прогноз саме
наступного виклику; резерв за потреби збільшується транзакційно.
Недостатній доступний баланс блокує виклик і за високого COMPUTE_MAX_USD.

Локальна обробка рядків після прийняття edit_xlsx не викликає модель повторно.
500 рядків у chunk — розмір контрольної точки, не максимальний розмір таблиці.
Inspect теж є локальною дією; XLSX inspect тепер враховує runMs і залишок totalMs.

Зберігаються: максимум 2048 вихідних токенів продовження; контекст 256 KiB / 65536
оцінених токенів разом із виходом; 60 с на Python-дію; 10 хв на модельний цикл;
XLSX 20 000 000 байт, 128 MiB після розпакування, 64 MiB на ZIP part;
512 MiB heap XLSX worker; chunk до 500 рядків / 1 MiB; staging до 96 MiB;
до 32 операцій у плані; 5 хв на фазу фонового XLSX worker; 24 год на job.
Ці межі не блокують тестовий файл 3 088 603 байти / 10 000 рядків за розміром.
Окремі помилки бюджету, контексту, формату або середовища все ще можливі.
PDF на 10 000 сторінок цим патчем не реалізується.

## Що змінено крім ENV-перевірки

- Ledger приймає унікальні phase до 32; begin усе одно перевіряє фактичний
  COMPUTE_MAX_CALLS. Зниження налаштування не ламає читання старих receipt IDs.
- Responses більше не зупиняє computation на прихованій межі 6 загальних
  викликів; ліміт продовжень узгоджений із Chat Completions. Звичайний цикл
  без computation зберігає свою попередню межу.
- Серверні DTO та frontend parser приймають нові лічильники без обрізання.
- Бюджетна відмова зберігає числові limit/spent/estimate/projected і тарифи
  в computeState.budgetRejection, поза rollback транзакції відмови.
- workerRuntime.computeLimits показує фактичні налаштування процесу при claim;
  новий revision — document-testing-limits-v2.
- Діагностика версії 3 показує бюджетну відмову та computation фінальної
  assistant message, навіть коли providerResult уже очищений після commit.

## Встановлення й перевірка

1. В окремому тестовому checkout застосувати backend.patch поверх 19eae54 /
попереднього handoff patch:

```bash
git apply --check ./GPTiti-Document-Testing-Limits/backend.patch
git apply ./GPTiti-Document-Testing-Limits/backend.patch
```

Нова залежність або міграція індексів не потрібна. Конфлікти не обходити через
--reject/force: звірити базу й локальні зміни. Тести запускати лише на окремій
disposable Mongo replica set; FILES_TEST_MONGO_URI має DB gptiti_files_test_*.
CHAT_V2_TEST_MONGO_URI теж лише для тестового кластера. OpenAI замоканий;
для тестів використати фіктивний OPENAI_API_KEY та тестовий JWT_SECRET.
У базовому оточенні автотестів не задавати чотири testing ENV override:
самі сценарії перевіряють типові, підвищені та знижені значення.

```bash
npm run test:compute
npm run test:compute:integration
npm run test:responses
npm run test:docx
npm run test:docx:integration
npm run test:document-jobs
npm run test:document-jobs:integration
npm run test:chat-v2:worker
npm run test:reservations
```

2. Злити й розгорнути окремий frontend PR до тестів із підвищеними лімітами.
Він сумісний зі старими значеннями й не змінює дизайн.

3. Перед зміною running code зупинити всі процеси саме цього backend звичайним
deployment-процесом; після встановлення запускати їх узгоджено з одного релізу.
Не зупиняти сторонні застосунки. Для перевірки PM2 без виводу ключів:

```bash
node scripts/inspectPm2Workers.js > pm2-workers-safe.json
```

Цей файл містить тільки name/id/pid/status/start/cwd/script/mode, без env і args.
Порівняти процеси backend з pid/loadedAt/bootId у діагностиці. Перевірка PM2
не виключає існування окремого контейнера або systemd worker на іншому хості.

4. На сервері застосувати вже перевірений patch тими самими командами git apply.
Додати чотири значення testing.env.example у чинну конфігурацію розгортання.
Для PM2 передати їх також у фактичне середовище процесу, наприклад:

```bash
COMPUTE_MAX_USD=1.00 COMPUTE_MAX_RUNS=12 COMPUTE_MAX_CALLS=16 COMPUTE_TOTAL_MS=300000 pm2 restart backend --update-env
```

У CHAT_V2_WORKER_READY перевірити revision=document-testing-limits-v2 і
computeLimits: usd=1, runs=12, calls=16, totalMs=300000. Запуск CLI або зміна
лише .env не доводять, що PM2 використовує ці значення.

5. Один T1 на оригінальному GPTiti_QA_10000_rows.xlsx у новому чаті. Очікується
QA_T1_result.xlsx: E2:E10001 помножено на 2, G2:G10001=ГОТОВО, решта незмінна;
сума E після перерахунку 100015000. Перевірити завантажений файл, формули,
стилі й одноразове списання. Потім той самий оригінал додати з Library у новий
запит і порівняти результат. Подальші F5/Cancel/SIGKILL — за існуючим QA.

```bash
node scripts/diagnoseDocumentTurn.js --recent-xlsx > document-diagnostic-testing.json
```

Якщо повториться відмова, у новому звіті будуть її точні числа та runtime.
Не вважати status=completed доказом наявності готового XLSX.

## Повернення до нижчих лімітів

Після тестів змінити чотири ENV-значення й перезапустити узгоджений backend.
Для точного повернення: 0.20 / 5 / 6 / 180000. Код і фронт відкочувати не треба.
Зменшувати краще між активними модельними запитами; вже прийняті фонові jobs
продовжують локальне виконання зі своїми контрольними точками.
Налаштовувати за журналами успішних задач: кількість кроків, фактичний і
прогнозований бюджет, час, відновлення й відмови. Не вимикати перевірку балансу,
резервування, ідемпотентність, квоти або перевірку незмінності оригіналу.
