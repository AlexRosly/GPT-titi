# MongoDB после переноса с Atlas на Ubuntu

Чтение коллекций и `ping` могут работать на standalone MongoDB. Chat V2, резервы, баланс и файловое хранилище используют транзакции, которым нужен replica set. `db.hello()` с `setName: null` показывает standalone. Старый документ ChatTurn со статусом `USER_CANCELLED` не диагностирует новую ошибку отправки после переноса.

Для установленного системного `mongod` на `127.0.0.1:27017`, когда MongoDB-пользователь приложения имеет только `readWrite`, подготовлен операторский скрипт. Он запускается **на VPS под root, из корня backend**, читает локальный URI из `.env` и не подходит для Docker/Atlas/шардирования/TLS.

Сначала отправьте изменения в Git и обновите checkout на VPS. Проверка без изменений:

```sh
cd /root/server/GPT-titi
node scripts/enableLocalMongoReplicaSet.js
```

Применение для текущего PM2 backend с ID 1:

```sh
node scripts/enableLocalMongoReplicaSet.js --apply --pm2-id=1
```

Скрипт останавливает backend, делает `mongodump` приложения и копии `.env`/`mongod.conf` в `/root/mongo-migration`, создаёт keyfile с правами сервисного пользователя, включает `rs0` и ждёт PRIMARY. Для инициализации при отсутствии MongoDB-администратора временно используется режим обслуживания **только на loopback**, затем авторизация обязательно включается обратно с keyfile. Другие локальные приложения/фоновые обработчики, которые пишут в эту БД, на время обслуживания тоже должны быть остановлены.

Создаётся отдельная административная учётная запись со случайным паролем в root-only JSON-файле в `/root/mongo-migration`. Учётные данные не печатаются. Приложение продолжает использовать прежний `gptiti_app` с прежним паролем и правами на свою БД. `MONGO_URI` и `CHAT_RECONCILIATION_MONGO_URI` получают `replicaSet=rs0&directConnection=true`; PM2 перезапускается с теми же значениями, поэтому старое окружение PM2 не перекрывает обновлённую `.env`.

В конце выполняется read-only проверка snapshot-транзакции с её отменой. Ожидается `transactionReadPassed: true`. При ошибке исходный защищённый конфиг восстанавливается, backend остаётся остановленным для проверки; скрипт печатает путь к резервной копии. Автоматически восстанавливать архив поверх БД он не будет. Один узел даёт поддержку транзакций, но не отказоустойчивость.

После успешного завершения:

```sh
pm2 logs 1 --lines 60 --nostream
```

Отправьте новое обычное сообщение через интерфейс. Не используйте старый отменённый turn как подтверждение работы нового backend. Если отправка опять не проходит, неожиданная ошибка теперь выводится как `CHAT_V2_REQUEST_ERROR` с событием и кодом MongoDB без URI, паролей и содержимого сообщения.

Проверки конфигурационных преобразований:

```sh
node --test test/localMongoReplicaSet.test.js
```

Официальные инструкции: [преобразование standalone в replica set](https://www.mongodb.com/docs/v8.0/tutorial/convert-standalone-to-replica-set/), [внутренняя аутентификация keyfile](https://www.mongodb.com/docs/manual/tutorial/deploy-replica-set-with-keyfile-access-control/).
