# GPTiti: патч постійної бібліотеки файлів для Алекса

База бека: `74ef7f09d339f1626335aeaed785717e52f70431` (main, OCR patch42).
Фронт: https://github.com/YourPriceBooking/GPTiti/pull/242

## Що змінено

- Успішно завершені приватні завантаження мають `retention: library`, `expiresAt: null`. Видалення вкладення з чернетки або очищення/архівація чату не видаляє файл.
- Згенеровані результати також постійні. Проміжні Python-експорти мають `retention: temporary`, живуть годину, не відображаються у Files. V2 переводить результат до library під час фіналізації відповіді. Заміна проміжного експорту не може видалити вже опублікований файл.
- DELETE скасовує preparation job у тій самій Mongo-транзакції, знімає lease, видаляє chunks/кеші й повертає квоту один раз. Наявні транзакції запису OCR/ZIP перевіряють власника/стан перед записом і конфліктують із видаленням. Історія повідомлень залишається; вкладення стає недоступним.
- GET /files приховує temporary та expired, повертає createdAt; усі файлові відповіді private/no-store. Ліміти повертають `storage.libraryVersion: 1`, `retention: until_user_deletes`, `unattachedTtlSeconds: null`.
- Нових HTTP-маршрутів не потрібно. Наявні upload/list/metadata/limits/preview/download/delete та OCR/preparation/V2 залишаються. Квота за замовчуванням — 2 000 000 000 байтів і 500 файлів; FILES_USER_BYTES/FILES_USER_COUNT мають пріоритет. Квота включає похідні OCR/ZIP-дані та тимчасові експорти до їх очищення.
- Дублікати одного fileId у запиті відхиляються; повторне використання в різних запитах не створює файл і не збільшує квоту. Модель отримує лише явно передані вкладення та штатний контекст історії.

## Застосування

Спочатку на staging. Не накладати поверх незакомічених змін. Якщо сервер уже має інший commit — спочатку `git apply --check`; при конфлікті потрібне перенесення змін, не `--reject` і не перезапис файлів.

```bash
git status --short
git rev-parse HEAD
git switch -c feature/persistent-file-library
git apply --check /path/to/gptiti-file-library-backend.patch
git apply /path/to/gptiti-file-library-backend.patch
npm ci
npm run test:files:library
npm run test:compute
npm run test:files
```

Для інтеграційних тестів потрібна окрема MongoDB replica set. Тести видаляють тестову БД. Не задавати production URI:

```bash
export FILES_TEST_MONGO_URI='mongodb://127.0.0.1:27017/gptiti_files_test_library?replicaSet=rs0'
npm run test:files:integration
```

Набір включає повторне використання у двох чатах, clear/archive, чужий акаунт і 404, HTTP upload/list, конкурентне видалення/квоту, видалення під час OCR, тимчасові результати, міграцію/dry-run/повторний запуск/пошкодження/квоту. Додатково запустити прийняті на сервері V2 DoD/reservations тести в їх окремій тестовій БД.

## Міграція наявних приватних файлів

Зробити узгоджений backup MongoDB. Зупинити **всі** API/PM2, cleanup, V2 та preparation workers на час фінального звіту й застосування, щоб старий cleanup не видалив файл паралельно з міграцією. MongoDB лишається запущеною. Після застосування коду використовуються штатні MONGO_URI/MONGODB_URI із серверного .env.

```bash
npm run db:indexes:files
npm run db:migrate:file-library
```

Без аргументів це dry-run: жодного перенесення, видалення чи зміни квоти. Перевіряє власників, послідовність chunks, розмір і SHA-256; звіряє суму оригіналів + derivedBytes та кількість з FileQuota. `problems` має бути порожнім. При проблемах код виходу 2 і міграція нічого не змінює.

```bash
FILE_LIBRARY_MIGRATION_OFFLINE=yes npm run db:migrate:file-library -- --apply
npm run db:migrate:file-library
```

Повторний запуск безпечний: `promoted: 0` після успіху. Поле promoted у dry-run — планована кількість. Після збою можна повторити: вже перенесені файли не дублюються.

Якщо є лише `QUOTA_MISMATCH`, спочатку перевірити звіт/backup. Окрема явна опція дозволяє перерахувати лічильники з наявних ready-записів:

```bash
FILE_LIBRARY_MIGRATION_OFFLINE=yes npm run db:migrate:file-library -- --apply --repair-quota
```

Пошкоджені chunks або відсутній власник блокують і цей режим. Перевищення актуальної квоти не видаляє даних: наявні файли доступні, нові upload блокуються штатним quota admission.

- Переносяться доступні private uploads та вже опубліковані generated-файли, з тими самими ID, без копіювання байтів.
- Expired/deleted не відновлюються. Expired залишаються під штатним cleanup; tombstones залишаються для захисту від повторного створення результатів.
- Старі generated-записи з expiresAt вважаються проміжними і зберігають TTL.
- `legacyFiles` — кількість старих FileModels/Cloudinary-записів. Патч не завантажує зовнішні URL і не імпортує їх автоматично: для них потрібна окрема перевірка власників і перенесення. Вони залишаються в старих чатах за чинними правилами, але до Files не додаються.
- Незавершений multipart не має ready-файла: spool видаляється ще до приймання байтів і закривається при cancel/crash; неуспішна транзакція не залишає quota/chunks. Якщо upload закомічений, але відповідь клієнту загубилась, файл уже в бібліотеці — спочатку refresh, не автоматичне повторне завантаження.

## Увімкнення фронта

Після міграції запустити оновлений бек. PRIVATE_FILES_ENABLED має залишатися true; чинні OCR/preparation налаштування не змінювати. Переконатися, що /files/limits повертає libraryVersion=1.

Змерджити PR #242 і зібрати фронт з `NEXT_PUBLIC_FILE_LIBRARY_ENABLED=true` (це build-time змінна Next.js). До готовності бека прапорець лишається вимкненим.

На staging: два різні акаунти; файл у двох чатах і незмінна квота; clear/archive не чіпає Files; delete недоступний всюди без втрати історії; generated після відповіді; OCR cancel/F5/Continue; ліміти; мобільний + picker; чернетка після Files і F5. Видалення з поля запиту не викликає DELETE. Cancel у новому фронті лише перестає чекати OCR, щоб не скасувати спільну роботу іншого чату.

Звичайний локальний файл у чаті, як і раніше, завантажується на Send. Files-page upload зберігає одразу. F5 зберігає текст і saved ID, але локальні байти до upload потрібно вибрати знову.

## Відкат

Насамперед вимкнути фронтовий прапорець і перебудувати фронт. Не повертати старий backend із delete-on-chat-clear поверх мігрованої бази: він знову зможе видаляти файли бібліотеки. Для повного відкату потрібні зупинка writers та узгоджене відновлення backup з урахуванням нових завантажень. Зворотна data migration навмисно відсутня.
