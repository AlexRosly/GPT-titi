# Модели Responses API — ноябрь 2026

Четыре модели используют `client.responses.create`. Маршрут задаёт поле `ChatModels.apiMode`, а уровень рассуждения — `reasoningEffort`. У существующих записей без `apiMode` сохраняется Chat Completions.

| Название | Точный API ID | apiMode | reasoningEffort |
| --- | --- | --- | --- |
| GPT-6 Luna | `gpt-6-luna` | `responses` | `none` |
| GPT-6.1 Terra | `gpt-6.1-terra` | `responses` | `low` |
| GPT-6.1 Sol | `gpt-6.1-sol` | `responses` | `medium` |
| GPT-6 Astra | `gpt-6-astra` | `responses` | `medium` |

Сохраняем `gpt-5.4-mini`, `gpt-5.4`, `gpt-5.5`. Скрипт каталога убирает из выбора `o1`, `o3-mini`, `gpt-4o`, `gpt-4o-mini`, `gpt-5.1` и их датированные версии через `enabled: false`. Записи моделей, переписки, сообщения и ссылки на использованную модель остаются в БД.

## Что реализовано

- Адаптер получает уже подготовленную историю. Правила выбора сообщений, OCR, чтения вложений и проверки доступа сохраняются. Текст и изображения преобразуются в `input_text` / `input_image`.
- Системные инструкции передаются при каждом шаге. Используются `stream: true`, `store: false` и `include: ["reasoning.encrypted_content"]`. Полная локальная история не смешивается с `previous_response_id` или Conversations API.
- Текстовые дельты поступают в существующий `chat:stream`. Идентификаторы Chat V2, `attempt`, `seq`, `chat:status`, дедупликация и сохранение результата перед списанием сохраняются.
- Для функций сохраняются исходные output items, включая reasoning. Аргументы исполняются только из завершённой функции в `response.completed`, после разбора JSON и проверки схемы/политики инструмента. Несколько вызовов получают отдельные `function_call_output`; затем модель продолжает работу.
- `create_file`, сохранённая дословная расшифровка, вычисления и собственный браузер используют действующие серверные реализации. Вебконтекст передаётся после существующей подготовки страниц. Встроенные инструменты OpenAI не подключаются.
- Обычный цикл ограничен шестью запросами к модели; вычисления и браузер дополнительно сохраняют прежние лимиты времени, запусков, файлов и бюджета. Вычисления используют общий исполнитель sandbox с Chat Completions.
- Обрыв, `incomplete`, `failed`, ошибка и отмена не трактуются как успешный финальный ответ. `providerResponseIds` сохраняются в ChatTurn. Неопределённый расход остаётся на существующем механизме reconciliation; автоматического повторного запроса к провайдеру нет.
- Usage суммируется по фактически завершённым ответам. Формулы цен и резервирования остаются прежними; новые тарифы в этой задаче не задаются.

Для отмены сервер принимает событие `chat:cancel` с таким же envelope, как `chat:status`, и возвращает ack со snapshot:

```json
{
  "protocolVersion": 2,
  "event": "chat:cancel",
  "type": "request",
  "payload": { "turnId": "UUID_ЗАПРОСА" }
}
```

Доступ проверяется по владельцу. Для очереди резерв освобождается однократно. Выполняющийся запрос получает AbortSignal; другие процессы видят флаг отмены через heartbeat. Если результат провайдера уже сохранён, сервер завершает его фиксацию. После F5 клиент запрашивает `chat:status`, не создаёт новый `clientMessageId` для той же отправки. Подключение кнопки Cancel и проверка её состояния на фронтенде входят в приёмку интерфейса.

## Подготовка каталога на сервере

Из корня проекта, с настроенным `MONGO_URI` в `.env`:

```sh
npm ci
npm run test:responses
npm run models:preview
npm run models:apply
```

`preview` только читает БД. `apply` выполняет транзакцию, выключает указанные старые модели и создаёт четыре новые записи с `enabled: false`. Резервная копия изменяемых записей сохраняется в `backups/model-catalog/`; директория исключена из Git. Нужен MongoDB replica set / Atlas. Повторный запуск не создаёт дубликаты. Если новая модель уже включена или обнаружены дубликаты ID, скрипт останавливается для проверки конфигурации.

После выкладки кода перезапустите backend обычной командой проекта, например для текущего PM2-процесса:

```sh
pm2 restart 1 --update-env
pm2 logs 1 --lines 60 --nostream
```

Откат конфигурации каталога с конкретным файлом, напечатанным после `apply`:

```sh
node scripts/updateModelCatalog202611.js --restore=backups/model-catalog/ИМЯ_КОПИИ.json
```

Восстановление проверяет сервер/название БД. Созданные миграцией черновики остаются выключенными; исторические данные не удаляются. Если отключённая старая модель была моделью по умолчанию, перед релизом выберите default среди трёх сохраняемых моделей в административной конфигурации.

## Проверки ключей и платные пробы

Установленная версия SDK OpenAI 6.15.0 поддерживает этот адаптер; обновление зависимостей не потребовалось. Ключи не выводятся в отчёты. Скрипт сам загружает `.env`; для другого файла используйте `--env-file=ПУТЬ`.

Проверка доступности без генерации:

```sh
npm run models:check -- --key-env=OPENAI_API_KEY --label=development
```

Платная короткая проверка «функция → результат → финальный ответ» для всех четырёх моделей:

```sh
npm run models:check -- --key-env=OPENAI_API_KEY --label=development --live --report=responses-development.json
```

Платная проверка DOCX/XLSX, переданного текста OCR и истории, с реальным созданием Office-контейнеров в памяти:

```sh
npm run models:check -- --key-env=OPENAI_API_KEY --label=development --live --files-only --report=responses-files-development.json
```

Повторите проверки для Production, указав соответствующий env-файл/имя переменной и `--label=production`. Название label — отметка в отчёте, оно не переключает OpenAI project или ключ. Для ключа без установленной принадлежности используйте `--label=configured`. Пробы не меняют каталог, не создают тестовых БД и не записывают файлы в пользовательские чаты.

## Результат локальной проверки 09.11.2026

- Ключ `OPENAI_API_KEY` из корневого `.env`: все четыре точных ID доступны; у каждой модели прошёл реальный цикл функции с финальным ответом. Отчёт: [responses-access-configured.json](responses-access-configured.json).
- Все четыре модели создали DOCX и XLSX, сохранив контрольный код из подготовленного текста OCR и предшествующей истории. Проверены Office-контейнеры и финальные ответы после функции. Отчёт: [responses-files-configured.json](responses-files-configured.json).
- Пройдено 39 тестов `npm run test:responses` и 128 регрессионных тестов, без ошибок и пропусков. Они проверяют Responses, Chat V2, обрывы/ошибки, отмену, восстановление, инструменты и миграцию, используя подмены провайдера и БД. Регрессионные тесты проверяют также существующие файлы, браузер, вычисления и вебконтекст.

Эти пробы подтверждают работу адаптера с реальным API и рендерером Office. Они не подтверждают скачивание из пользовательского чата через HTTP, реальную OCR-обработку изображения, работу Docker sandbox/браузера на VDS или поведение фронтенда после Cancel/F5.

Принадлежность локального ключа к Development/Production пока не установлена. Перед публичным включением нужны отдельная отметка о проверке обеих сред и приёмка для каждой модели: украинский ответ со стримингом; продолжение истории; реальное вложение/OCR; создание и скачивание DOCX/XLSX; несколько шагов инструментов; Cancel; F5 во время генерации; ошибка/обрыв; недоступный ID без подмены. Также заполните реальные `inputPerM` / `outputPerM`, отображение модели и необходимые лимиты. Затем включайте `enabled` у прошедших приёмку моделей.

Во время локальной разработки выполнен только preview каталога; `models:apply` к настроенной БД не запускался, выкладка на VDS не выполнялась.
