## Необхідні змінні .env для WebSocket
Для налаштування WebSocket-сервера потрібно вказати у `.env` тільки такі змінні:

```
SOCKET_CORS_ORIGINS=http://localhost:3000,https://www.gptiti.com
SOCKET_CREDENTIALS=true
```

**Пояснення:**
- `SOCKET_CORS_ORIGINS` — список дозволених origin для WebSocket (через кому)
- `SOCKET_CREDENTIALS` — чи дозволяти credentials (true/false)

# Інструкція для backend: як додавати нові підписки та емiти через WebSocket



## Загальна архітектура
Сервер використовує універсальний протокол повідомлень через канал `ws:message` (див. src/wsServer.js). Всі події між фронтом і сервером проходять через цей канал з об'єктом формату:

```
{
	event: string,        // назва події
	type: string,         // тип повідомлення (request/response/error тощо)
	requestId: string,    // id запиту для співставлення відповідей
	payload: object       // корисне навантаження
}
```

## Як додати нову підписку сервера на повідомлення від фронта
1. Відкрийте файл `src/wsServer.js`.
2. Усередині обробника `io.on('connection', (socket) => { ... })` додайте нову гілку в обробнику події `socket.on('ws:message', ...)`.
3. Перевірте поле `event` у вхідному повідомленні та реалізуйте потрібну логіку.

**Приклад:**
```js
// ...existing code...
socket.on('ws:message', async (msg) => {
	const { event, type, requestId, payload } = msg;
	if (event === 'myCustomEvent') {
		// Ваша логіка обробки
		// Наприклад, надіслати відповідь:
		socket.emit('ws:message', {
			event: 'myCustomEvent',
			type: 'response',
			requestId,
			payload: { result: 'ok' }
		});
	}
	// ...existing code...
});
// ...existing code...
```

## Як відправити нову подію з сервера на фронти
1. Імпортуйте функцію `getIo` з `src/wsServer.js` у потрібному місці backend.
2. Отримайте екземпляр io: `const io = getIo();`
3. Використовуйте `io.emit('ws:message', { ... })` для відправки події всім фронтам, або `socket.emit(...)` для конкретного користувача.

**Приклад:**
```js
const { getIo } = require('./wsServer');
const io = getIo();
io.emit('ws:message', {
	event: 'notifyAll',
	type: 'info',
	requestId: null,
	payload: { message: 'Важливе повідомлення' }
});
```

## Best practices
- Завжди використовуйте універсальний формат повідомлення.
- Для відповідей на запити використовуйте той самий `requestId`, що і в запиті.
- Для broadcast-повідомлень використовуйте `io.emit`, для персональних — `socket.emit`.
- Не додавайте нові socket.io події, використовуйте лише `ws:message`.
- Документуйте нові типи подій і payload у цьому README або окремому файлі.

## Перевод токенов между пользователями

Backend предоставляет два авторизованных маршрута для формы Send tokens. Базовый путь — `/gpt-titi/api/users`, заголовок авторизации — `Authorization: Bearer <accessToken>`. Отправитель должен иметь статус `active`. Получатели со статусами `active` и `blocked` могут принимать токены; после успешного перевода `blocked` становится `active`. Для `deleted` перевод запрещён, ответ поясняет, что пользователь удалил аккаунт. Перевод самому себе запрещён.

### Проверка получателя

`GET /gpt-titi/api/users/token-transfers/recipient?email=alex%40example.com`

Email очищается от пробелов по краям, приводится к нижнему регистру и сравнивается с email в БД без учёта регистра, как обычная строка. Успешный ответ (`200`):

```json
{
  "success": true,
  "canTransfer": true,
  "recipient": { "email": "alex@example.com", "status": "blocked" },
  "appTokens": 594814
}
```

Проверка не резервирует баланс. При отправке сервер повторно проверяет пользователя, статус получателя и баланс внутри транзакции.

### Выполнение перевода

`POST /gpt-titi/api/users/token-transfers`, `Content-Type: application/json`:

```json
{
  "email": "alex@example.com",
  "amount": 1000,
  "clientTransferId": "2d119c58-f40c-4c75-b866-797118cc22ca"
}
```

`amount` — положительное целое JSON-число, не превышающее `9007199254740991`. Строки, дроби, ноль и отрицательные значения отклоняются. `clientTransferId` — обязательный UUIDv4, созданный клиентом один раз для конкретного намерения перевести токены. Успешный ответ (`200`):

```json
{
  "success": true,
  "transfer": {
    "id": "507f1f77bcf86cd799439011",
    "clientTransferId": "2d119c58-f40c-4c75-b866-797118cc22ca",
    "email": "alex@example.com",
    "amount": 1000,
    "createdAt": "2026-09-23T12:00:00.000Z"
  },
  "appTokens": 593814,
  "alreadyApplied": false
}
```

Списание, зачисление, активация заблокированного получателя и запись перевода выполняются одной транзакцией. При повторном запросе с тем же отправителем, `clientTransferId` и нормализованными email/суммой сервер возвращает исходную квитанцию с `alreadyApplied: true` без повторного списания. Тот же ID с другим email или суммой возвращает `409 IDEMPOTENCY_CONFLICT`. Поле `appTokens` в квитанции отражает баланс сразу после исходного перевода; при `alreadyApplied: true` оно может отличаться от текущего баланса.

### Ошибки и поведение формы

Ошибки перевода имеют вид `{ "success": false, "code": "RECIPIENT_DELETED", "message": "..." }`. Ошибки авторизации сохраняют существующий формат `{ "error": "..." }` и статус `401`.

| HTTP | Код | Причина |
| --- | --- | --- |
| 400 | `INVALID_EMAIL` | Некорректный email. |
| 400 | `INVALID_AMOUNT` | Сумма не является положительным безопасным целым JSON-числом. |
| 400 | `INVALID_CLIENT_TRANSFER_ID` | Отсутствует или некорректен UUIDv4. |
| 400 | `SELF_TRANSFER` | Получатель и отправитель — один пользователь. |
| 403 | `SENDER_NOT_ALLOWED` | Отправитель не имеет статуса `active`. |
| 404 | `RECIPIENT_NOT_FOUND` | Получатель не найден. |
| 409 | `RECIPIENT_DELETED` | Пользователь удалил аккаунт; перевод невозможен. |
| 409 | `RECIPIENT_UNAVAILABLE` | Неподдерживаемый статус, неоднозначный email или переполнение баланса получателя. |
| 409 | `INSUFFICIENT_BALANCE` | Недостаточно токенов; ответ дополнительно содержит `appTokens`. |
| 409 | `IDEMPOTENCY_CONFLICT` | ID перевода уже использован с другим email или суммой. |
| 500 | `INTERNAL_ERROR` | Внутренняя ошибка сервера. |

Интеграция формы на фронтенде:

1. Проверять email с задержкой около 300 мс после ввода. При изменении email сбрасывать подтверждение получателя и игнорировать ответы на устаревшие запросы.
2. Разрешать отправку только для подтверждённого текущего email, положительного целого количества токенов и достаточного баланса. Кнопка Max использует `Math.max(0, appTokens)`. На время отправки блокировать повторное нажатие.
3. Создавать новый `clientTransferId` для каждого нового намерения выполнить перевод. После сетевой ошибки или неизвестного результата повторять исходный payload с прежним ID: новый ID может привести к повторному переводу.
4. Обрабатывать ошибки POST даже после успешной проверки email: статус или баланс могли измениться. При `INSUFFICIENT_BALANCE` обновлять доступный баланс из ответа. При `RECIPIENT_DELETED` показывать сообщение об удалённом аккаунте.
5. После успешной отправки показывать подтверждение. Для повторно полученной квитанции (`alreadyApplied: true`) не заменять текущий баланс приложения историческим значением из квитанции. Актуальный `appTokens` можно получить повторной успешной проверкой получателя через `GET /gpt-titi/api/users/token-transfers/recipient`.

В этом репозитории реализован API. Кода формы здесь нет; её нужно подключить к описанным маршрутам во фронтенде.

### Подготовка БД и проверка

Для транзакций нужен MongoDB replica set или MongoDB Atlas. Перед включением переводов выполните `npm run db:indexes:token-transfers` с настройкой подключения `MONGO_URI`. Скрипт создаёт обязательный уникальный индекс журнала переводов по отправителю и `clientTransferId`, защищающий от повторного выполнения одного перевода, а также индекс `email_case_insensitive` для поиска получателя без учёта регистра. Существующие индексы сохраняются.

Проверки запускаются командой `npm run test:token-transfers`. Для интеграционных проверок укажите `TOKEN_TRANSFER_TEST_MONGO_URI` с подключением к тестовому MongoDB replica set; также поддерживается резервная переменная `CHAT_V2_TEST_MONGO_URI`.
